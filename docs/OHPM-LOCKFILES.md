# OHPM v3 lockfile inventory · Issue #3 / M1

When an [OHPM manifest](OHPM-MANIFESTS.md) is selected, ArkCompat reads the adjacent `oh-package-lock.json5` v3 format. The [Huawei lockfile reference](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/ide-oh-package-json5/) describes its purpose; the parser is scoped to the layout checked against actual DevEco-generated locks.

The graph resolves direct and recorded package dependency edges through exact `specifiers` entries to their matching `packages` records. It does not infer a resolution by name, read installed packages or validate integrity. Standard semver ranges are compared with the exact registry version; disagreement yields `mismatch` while retaining the recorded node ID, and tags/non-semver local protocols remain unchecked. A registry locator carries a valid exact version; when the record also supplies a version, the two must agree. Stale selectors stay missing; unsupported registry and alias records do not attach to an unrelated name. Local HARs can contribute the name and recorded version with an opaque node ID. Their relationship is unsupported for installation or compatibility verification. Paths, registry URLs and integrity values from the lock are not exported.

A v3 lock explicitly marked unified is projected only for a [configured OHPM project](OHPM-MODULES.md). Its table is parsed once, and root/module reports include only nodes reachable from their exact declarations. Module-local `file:` selectors are normalized to the root-relative form observed in DevEco-generated unified locks. Absolute or escaping references remain unsupported with no node attached. A shared 20,000-edge limit bounds the combined projections.

Other versions, standalone unified locks, target-specific graphs, overrides, and dynamic dependency resolution remain outside this slice. The report explicitly falls back to declarations for unsupported selected formats. Malformed recognized v3 data or unsafe selected files fail with a bounded diagnostic. The [project module inventory](OHPM-MODULES.md) can show independent adjacent locks together.

Schema 0.7.0 introduced the OHPM graph source and `ohpm-lockfile-partial` coverage. Schema 0.12.0 adds explicit semver `mismatch` across supported lock families. Rebuild all consumers together and rescan: current strict consumers require [schema 0.12.0](DEPENDENCY-RANGE-VALIDATION.md), and historical artifacts should keep their original version. Other manager graph shapes and unknown-only compatibility semantics are unchanged.

The actual DevEco API 20 build generated separate locks. The Lottie project's root yielded two recorded registry dependencies, and its entry yielded one recorded local HAR version with an unsupported edge and a redacted specifier. A second actual build enabled the unified setting and produced the same scoped direct results from its single root lock. Authored regressions cover transitive selection, mismatched and stale entries, and schema/CLI parity. No real package, dataset or candidate record is imported into ArkCompat by this adapter. No independent accuracy claim follows.
